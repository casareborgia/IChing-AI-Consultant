# 리포트 파이프라인 원인 분석 및 협업 체크리스트

기준일: 2026-09-06

## 결론

가족 사연에 비즈니스 문구가 보인 현상의 직접적인 재현 원인은 리포트 생성 실패와
프론트엔드 폴백이었다. 해석 에이전트는 `EvidenceItem` 객체를 넘겼지만 리포트
에이전트는 이를 딕셔너리로 간주해 `e.get(...)`을 호출했다. 근거가 있는 정상 경로에서
`AttributeError`가 발생했고, 파이프라인은 `report_data=None`으로 계속 진행했다.
프론트엔드는 이때 과거의 고정 해석 문구를 맞춤 리포트처럼 표시했다.

괘 도출 알고리즘과 변효 수에 따른 고변점 해석법은 이번 결함의 원인이 아니다.
고변점 해석법은 유지한다. 다만 지괘의 효를 핵심 대상으로 선택했을 때 실제 DB 조회도
지괘의 해당 효를 향해야 한다. 해석 규칙과 원문 조회의 정합성은 별개다.

## 확인된 결함과 조치

1. `EvidenceItem`과 딕셔너리를 모두 안전하게 읽도록 입력 경계를 정리했다.
2. 고변점 결과를 실제 `(hexagram_id, line_number)`로 변환한 뒤 원문을 조회한다.
3. 변효 0~6개와 건·곤 전효변의 용구·용육 경로를 테스트한다.
4. RAG 근거는 단순 앞 3건 절단 대신 핵심 괘·효와 일치하는 근거를 우선한다.
5. 초안 필드가 빠진 LLM 응답은 정상 리포트로 조립하지 않고 실패로 처리한다.
6. 리포트 실패 시 프론트엔드는 고정 해석을 만들지 않고 실패 상태를 표시한다.
7. Docker 빌드는 런타임 프롬프트 6종을 전부 검사한다.

## 프롬프트 프라이밍 가설 검증

`gemini-2.5-flash`에서 가족 질문 3개를 사용해 현재 프롬프트와 구체 예시 제거안을
각각 2회 비교했다. 질문·괘·효사·RAG 근거·온도는 고정했고 프롬프트의 구체 예시만
달리했다.

| 조건 | 생성 수 | 비즈니스 어휘 누출 |
|---|---:|---:|
| 현재 프롬프트 | 6 | 0 |
| 구체 예시 제거 | 6 | 0 |

이 표본에서는 구체 예시가 비즈니스 어휘를 직접 복제하게 한다는 가설이 확인되지
않았다. 따라서 이번 수정과 함께 운영 프롬프트를 변경하지 않았다. 표본이 작으므로
“프라이밍이 절대 없다”는 결론으로 확대하지 않는다. 재측정은
`scripts/compare_report_prompt_priming.py`로 수행한다.

## 변경 시 체크리스트

- 실제 서비스가 전달하는 Pydantic 객체와 JSON 딕셔너리를 모두 포함해 테스트한다.
- 모델 호출 여부와 프론트 폴백 여부를 분리해 관찰한다.
- 고변점의 대상 명칭, 대상 괘 ID, 효 번호, 조회 원문이 모두 같은 대상을 가리키는지 확인한다.
- 초점 효 주석이 최종 프롬프트에 실제로 포함됐는지 확인한다.
- `topic_category`가 Intake에서 리포트까지 전달되는지 확인한다.
- 프롬프트와 호출 설정을 동시에 바꾸지 않는다.
- 서비스 모델 비교에서는 질문·괘·근거·온도·반복 수를 고정한다.
- 필수 프롬프트 누락은 런타임 500이 아니라 이미지 빌드 실패로 잡는다.
- 리포트 생성 실패를 맞춤 해석 문장으로 감추지 않는다.
